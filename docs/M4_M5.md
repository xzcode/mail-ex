# M4 / partial M5 — OAuth, indexed search and batch operations

## OAuth (desktop application)
Google Workspace/Gmail, Outlook.com/Hotmail, and Microsoft 365/Exchange Online have separate fixed TLS endpoint presets. The app uses the system browser, OAuth 2.0 authorization code, PKCE S256, a random state, and an ephemeral loopback listener; cancellation and timeout are supported. Token requests go only to fixed official HTTPS token endpoints, with redirects disabled. Tokens (including optional Google desktop-client registration value) are encrypted with the existing per-install vault key, not returned to the webview. The app verifies IMAP inbox access before saving a new account or replacing a prior OAuth credential. Refresh is serialized across the current process and updates the encrypted credential; a replacement refresh token is retained, otherwise the previous one is reused. Refresh happens ahead of expiry, not by replaying a send. IMAP and SMTP use XOAUTH2 only for OAuth accounts; there is no password fallback.

Registration is bring-your-own-client for now. No project-owned registration, confidential client secret, hosted authorization service or provider approval is included. Do not claim Gmail/Outlook live compatibility until tested with an approved registration. The Microsoft consumer preset uses smtp-mail.outlook.com; Microsoft 365 uses smtp.office365.com. Microsoft IMAP/SMTP permissions or tenant policies may still block access. Google restricted Gmail scope may require verification. Reauthorization keeps the previous cache and requires the same mailbox/provider; new tokens replace old ones only after IMAP validation.

### Google setup
1. In Google Cloud, configure the OAuth consent screen and create a **Desktop app** OAuth client. Add test users while in testing mode.
2. Enter that client ID and, if issued/required, its desktop-client registration secret in the Mail EX OAuth dialog. Do not use web/server confidential credentials.
3. Grant the mail scope `https://mail.google.com/`; OAuth client approval and Workspace policies apply.

### Microsoft setup
1. Register a public client with the desired supported account types in Microsoft Entra. For system browsers configure Mobile and desktop applications with redirect `http://localhost`.
2. Configure delegated Exchange Online IMAP/SMTP permissions (`IMAP.AccessAsUser.All`, `SMTP.Send`), allow public client flows as appropriate, and grant consent.
3. Enter the client ID; no client secret is accepted. IMAP and authenticated SMTP must be available to the account. This version uses delegated IMAP/SMTP, not Graph or app-only access.

## M5 search and batch
Database schema v4 adds account authentication kind; v5 builds an FTS5 trigram external-content index for subject, sender, recipients and body, with insert/update/delete triggers. Existing HTML-only cache entries receive a sanitized text fallback for indexing. Three-or-more-character queries use literal quoted FTS phrases (not user-supplied query operators). One/two-character queries fall back to substring matching, including Chinese. Scope follows selected account/folder/unified view; filters include sender, recipient, subject and local-date range. Indexing is local only.

Multi-select can select all loaded rows or individual messages. Read/unread, star/unstar, move, archive and trash reuse UIDVALIDITY and server-confirmed mutation methods. Mixed-account archive/trash resolves a unique server-declared destination per account; manual destination selection is for one account. Per-message failures are reported, without global expunge or automatic retries. Current batch implementation performs sequential individual operations; connection reuse and cancellation remain follow-up.

Remaining M5: saved searches, rule editor and automatic rule execution, attachment-aware filters and thread/group views. M4 remaining: live provider authorization and actual desktop browser callback/runtime; Graph adapter only if needed. Native desktop build still separate from core/frontend checks.
